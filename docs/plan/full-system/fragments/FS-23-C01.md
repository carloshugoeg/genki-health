# FS-23-C01 — charges: engine-neutral use cases and memory OP68,69

Implementado y verificado dentro del contrato económico de la lane.

- Alcance: `charges`; sin cambios de auth ni composición global.
- Implementación: DTO/puerto existente, servicio, dominio, adaptadores y página/plugin independientes de este módulo.
- Evidencia y comandos compartidos: [FS-23-C01](FS-23-C01.md).

## Implementación y arquitectura

OP61–77 en seis servicios independientes. Los cuatro adaptadores escriben directamente en sus SDK/clientes nativos; no seleccionan memoria en caso de error. PostgreSQL/MySQL almacenan filas JSONB/JSON en tablas por entidad con claves compuestas por institución/identificador; `lane_a_contracts` mantiene el contrato separado del profesional. Mongo usa colecciones por entidad; Firestore usa documentos por entidad bajo `institutions/{id}/lane_a_*`. No se almacena el ledger entero en un documento.

Una exclusión por institución serializa el ledger: bloqueo de fila SQL, actualización de lock en transacción de réplica Mongo, lectura/escritura de lock en transacción Firestore. Es una decisión MVP: prioriza integridad sobre concurrencia y consultas masivas. Contadores de ID/serie, stock, cargos, líneas, pagos, saldo, auditoría e idempotencia participan de la misma transacción. Dinero calculado en centavos, IVA simulado del 12% solo para servicios afectos. No hay FEL ni pagos bancarios.

Los plugins reciben un repositorio y un proveedor **confiable** de `OperationContext`; no interpretan identidad ni permisos del payload. Mantienen las restricciones `cargo.autorizar` y liquidación RRHH/propia sin cambiar grants, JWT o sesiones. Las páginas reciben el cliente autenticado existente del host. No están montados en el router ni API global, conforme al brief.

`EconomicReferences` es un puerto de integración explícito para consultar pacientes/actos de la institución. El wiring clínico posterior debe implementarlo con lecturas nativas dentro del UoW; no se inventan tablas clínicas nuevas. PG/MySQL/Mongo exponen el contexto transaccional existente por ALS; Firebase acepta una fábrica de referencias que recibe la transacción nativa. Las fixtures de aceptación proporcionan referencias clínicas sintéticas explícitas: la evidencia nativa cubre exclusivamente las escrituras económicas de esta lane.

## Variables

Se reutilizan `DATABASE_URL`, `MYSQL_URL`, `MONGODB_URI` (réplica, base explícita), `FIREBASE_PROJECT_ID`, `FIRESTORE_EMULATOR_HOST`, `FIRESTORE_MODE` y `GOOGLE_APPLICATION_CREDENTIALS` para el modo real ya existente. Sin nuevos secretos, sin cambios de switches globales. El CLI exige URLs explícitas; nunca escoge memoria.

Solo verificación: `LANE_A_ENGINES=1` activa el contrato nativo, `LANE_A_ENGINE=postgres|mysql|mongodb|firebase` selecciona uno; sin selector exige los cuatro. `CHROMIUM_PATH` opcional para el smoke de navegador (predeterminado `/usr/bin/chromium`). `FIREBASE_EMULATORS_PATH` y `XDG_CONFIG_HOME` se usaron para cachés locales del emulador.

## Migraciones y seed

Desde la raíz del repositorio, con variables del motor configuradas:

```sh
for engine in postgres mysql mongodb firebase; do
  npx tsx server/test/full/charges/manage.ts migrate "$engine"
  npx tsx server/test/full/charges/manage.ts seed "$engine"
done
```

SQL: `server/src/adapters/{postgres,mysql}/full/{charges,personnel,inventory,honoraria,invoicing,payments}/migrations/001.sql`. Todas usan `CREATE TABLE IF NOT EXISTS`. Son migraciones aditivas independientes: el runner global no fue modificado. No sustituyen las migraciones clínicas existentes.

Mongo: `MongodbEconomicStore.migrate()` en `server/src/adapters/mongodb/full/charges.ts`, crea índices/colecciones y lock con `$setOnInsert`. Firestore no requiere DDL: documentos/colecciones se crean dentro de la transacción. SDK Admin, sin cambiar las reglas/configuración existentes ni abrir acceso desde el cliente.

Fixtures por módulo: `server/test/full/{charges,personnel,inventory,honoraria}/fixtures.ts`. Datos académicos, inserción solo si falta: dos servicios, dos categorías, un material con stock inicial 10, umbral bajo stock 5 y un rol. No crean usuarios, pacientes, actos ni profesionales; el profesional se crea mediante OP61 en el contrato. Repetir seed no repone stock consumido ni sobrescribe tarifas/datos existentes. Facturas y pagos no reciben fixtures de datos transaccionales. Sin cambios a `scripts/seed.ts`.

Resultados observados antes del push:

- PostgreSQL 16, MySQL 8 y MongoDB 7 (réplica): contrato nativo aprobado en cada motor. Migra y siembra dos veces; cargo → preview → factura → pago concurrente → lectura con conexión/adaptador nuevo, consumo idempotente, rollback forzado después de stock/consumo, honorarios históricos y anulación. Referencias clínicas de prueba sintéticas; sin fallback económico a memoria.
- Contrato de memoria y pruebas HTTP: aprobados. Todas las suites ordinarias: 102 pruebas de servidor y 8 de web aprobadas; cuatro pruebas nativas se omiten en la ejecución ordinaria y se ejecutan explícitamente por motor como se indica arriba.
- Navegador Chromium: seis páginas renderizadas, preview → factura conserva selección/hash, sin errores de página. Cliente académico controlado; no se presenta como E2E nativo.
- Firestore: implementación lista, **aceptación nativa no satisfecha**. La descarga oficial `cloud-firestore-emulator-v1.19.8.jar` devuelve `403 Domain forbidden` (`storage.googleapis.com`); no hay credenciales reales configuradas. Se pidió habilitar el dominio en el entorno. No se sustituyó por memoria ni se declaró aprobado.

## Límites MVP

Sin montaje global, cierre clínico/dental ni cambios de otros módulos: son responsabilidad del wire posterior expresamente reservado. Sin reembolsos automáticos, integración tributaria/bancaria ni matriz full77 E2E. Consultas y reportes leen filas de la institución y paginan/proyectan en aplicación; el lock de institución limita throughput. El brief no está completamente aceptado hasta aprobar el contrato nativo de Firestore.
